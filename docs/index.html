How it works GitHub

Go to bed. Wake up to reviewed PRs and a short list of questions.

stu turns your Claude Code session into a blind supervisor. It hands out the work, checks every return mechanically, and stops rather than guess.

Once
/stu:init

Answer a few questions about your repo.

Start
/stu:run "<objective>"

Name the work. Walk away.

After
/stu:settle

Answer what it parked, one at a time.

Install
/plugin install stu --marketplace keavi-app/stu-claude

Why long runs go wrong

  • Runs drift.Three hours in, the session is busy with work nobody asked for.
  • Agents self-certify."Done" is a word the agent typed.
  • Checks lie.A check that never ran looks the same as one that passed.
  • Questions get guessed.Calls you would have made differently, made at 3 a.m.
  • Pushes go unseen.The agent that wrote the change also ships it.

How stu works

A supervisor that stays small

Your session holds only unit IDs and a scoreboard, and never reads the work. Its context is designed to stay flat; if it grows anyway, the run ends at the next cycle.

  1. you
  2. supervisorholds: unit IDs, scoreboardreads: nothing
  3. orchestratorfresh each cyclewrites no code
  4. implementerwrites
    reviewerat one SHA
    merge gateown evidence
    scout, verifierread-only

Checks that stop the run instead of trusting it

Every return is checked against the scoreboard with set operations. A failure gets one repair at most, then the run stops.

  1. returnID sets
  2. five checks, every return
    1. 1every ID was issuedno invented work
    2. 2no silent new unitsno scope creep
    3. 3DONE means none leftno "done" with work open
    4. 4a premise to verifyno self-certified claims
    5. 5progress, not spinningno burned night
  3. all passscoreboard updated; next cycle, or DONE
    a failone repair, at most
    fails again: STOPfail closed, nothing guessed

Questions wait for you; the run keeps going

A question only you can answer parks one unit, with a recommendation. Settle it later in a fresh session.

  1. unit 3 needs youyour call
  2. parkedwith a recommendation
  3. others continueunits 1 and 2
  4. /stu:settleone at a time
  5. resumeanswers go back in

Repos you mark wait for your approval

On a marked repo, an agent's push stops at a git hook until you approve that exact commit. Elsewhere, the merge gate merges only the SHA that was reviewed.

Marked repo, agent push
  1. git pushfrom the agent
  2. before-pushrefused: not approved
  3. stu-approve <unit> <sha>you run it, not the agent
  4. pushthat SHA only
Your own push
  1. git pushyour terminal
  2. pushstraight through; public repos still get the leak scan
Unmarked repo
  1. reviewedby an agent that did not write it
  2. merge gatecollects its own evidence
  3. merged at the reviewed SHAor reported for you to merge

A budget on every agent

Turn and context budgets, enforced live by a hook, with a native maxTurns backstop. Each role gets the cheapest model that does the job.

RoleModelTurn budget
supervisoryour session4 cycles (8 overnight)
orchestratoropus on cycle 1, then sonnet120 · backstop 190
implementersonnet140 · backstop 220
reviewer, merge gate, verifiersonnet
scouthaiku
